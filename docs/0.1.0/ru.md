# File streams React 0.1.0 — вложение от формы до хранилища

[← Версии](../index.md) · [API](reference.ru.md) · [README](../../README.md) · [English](en.md)

В форме заявки нужно прикрепить файл. Интерфейс должен показывать прогресс, останавливать передачу при уходе пользователя, отличать подтверждённое сохранение от прочитанных байтов и скачивать файл без создания второй полной копии в памяти браузера. Эта работа повторяется в разных формах и не относится к бизнес-логике заявки.

Компоненты берут на себя жизненный цикл передачи. Приложение задаёт ключ объекта, endpoint с проверкой доступа, ограничения размера и назначение скачивания. Парный Spring-стартер подключает Java HTTP-адаптер и хранилище. Ниже воспроизводимые сценарии интеграции: это не утверждения о production-внедрении или измеренной скорости разработки.

## 1. Загрузить вложение из React и принять его в Java

Полный код: [Attachments.tsx](../../examples/attachments/Attachments.tsx). Комментарии к действиям расположены парами: сначала английский, следующей строкой русский.

```tsx
<FileUpload
  objectsUrl="https://127.0.0.1:19443/objects"
  scope="account-42"
  objectKey="tickets/123/attachment.bin"
  maxBytes={8 * 1024 * 1024}
  onCommitted={setSaved}
/>
```

На стороне Java тот же endpoint включается явно:

```yaml
file-streams:
  enabled: true
  s3:
    bucket: attachments
    region: us-east-1
  http:
    enabled: true
```

Используйте [Java-приложение](https://github.com/59Alex/file-streams-spring-boot-starter/blob/main/example/src/main/java/example/FileStreamsApplication.java) и [полный application.yml](https://github.com/59Alex/file-streams-spring-boot-starter/blob/main/example/src/main/resources/application.yml): там HTTP/2, TLS, region, endpoint и CORS. Локально эти файлы находятся в `../file-streams-spring-boot-starter/example/`. Credentials поступают из стандартной цепочки AWS; в React они не нужны.

| Действие React/браузера | Действие Java/сервера | Наблюдаемый результат |
| --- | --- | --- |
| Выбрать File и вызвать `stream()` | Сырое тело PUT поступает в существующий WebFlux-адаптер | Не нужны form-data parser и планирование частей в браузере |
| PUT `/objects/tickets%2F123%2Fattachment.bin`, заголовок `X-Upload-Length` | Проверить размер и читать поток с backpressure | Прогресс показывает прочитанные клиентом байты |
| Дождаться JSON `201` | Хранилище подтверждает запись; адаптер возвращает `{committed,key,bytes,etag}` | `onCommitted` вызывается только после проверки подтверждения |
| Отменить передачу или убрать компонент | AbortSignal передаётся транспорту; Java/хранилище освобождают ресурсы | Потеря ответа всё ещё может означать уже сохранённый объект |

В каждой новой форме не приходится заново связывать file input, прогресс, отмену и результат сохранения. Проверка доступа остаётся на сервере: он должен убедиться, что аккаунту 42 разрешена запись по ключу этой заявки.

## 2. Скачать файл прямо в назначение

Вторая часть [Attachments.tsx](../../examples/attachments/Attachments.tsx) передаёт в `FileDownload` фабрику, открывающую `showSaveFilePicker()` и возвращающую `createWritable()`. Фабрика вызывается по нажатию кнопки. GET использует тот же URL объекта; Java передаёт тело S3-объекта потоком и открывает через CORS заголовки `Content-Length`, `ETag`, `Accept-Ranges`, а для диапазона — `Content-Range`.

```tsx
<FileDownload
  objectsUrl="https://127.0.0.1:19443/objects"
  scope="account-42"
  objectKey={saved.key}
  maxBytes={8 * 1024 * 1024}
  destination={openWritableFile}
/>
```

Клиент ожидает каждую запись в sink, проверяет длину и метаданные, показывает завершение только после закрытия назначения. Можно передать другой `WritableStream`: например, OPFS или конвейер обработки. Скрытого накопления в `Blob` нет. Поддержка File System Access и потокового тела запроса различается между браузерами; демонстрация проверена в Chromium. Проверка конструктора потока сама по себе не подтверждает работу через прокси.

## 3. Передать отчёт, не собирая целый файл

[GeneratedReport.tsx](../../examples/attachments/GeneratedReport.tsx) создаёт строки CSV внутри `ReadableStream.pull`. `useFileUpload().upload()` принимает такой одноразовый поток с неизвестной длиной. Ограничение числа байтов продолжает действовать. На Java работает тот же PUT handler: второй API для сгенерированных файлов не требуется.

Этот вариант подходит для постепенно производимых данных. Передавайте `knownLength`, когда размер известен: в локальном HTTP/2 fixture после отмены потока неизвестной длины сохранился префикс 8 КиБ; точная причина завершения HTTP-потока не установлена. Клиент не получил подтверждения, но объект существовал. Неизвестная длина сама по себе не доказывает логическую полноту; если она нужна, приложение должно дополнительно проверять ожидаемый размер/хеш или использовать staging/finalization-протокол. Эти прикладные протоколы адаптер не предоставляет. Не нужны промежуточный `rows.join(...)`, сборка Blob и собственный механизм прогресса для каждого отчёта. Повтор выполняется явно: сначала выясните результат предыдущей попытки, затем создайте новый источник.

[CancelableImport.tsx](../../examples/attachments/CancelableImport.tsx) показывает отмену постепенного источника с объявленным размером 1 МиБ. Объявленная длина позволяет Java отклонить ранний EOF. Искусственная задержка делает её видимой в демо. После отмены `ABORTED` и `uploadOutcome: unknown` не доказывают откат записи на сервере.

## 4. Получить только нужный префикс

[PartialPreview.tsx](../../examples/attachments/PartialPreview.tsx) запрашивает байты 0–4095 и сохраняет только небольшой предварительный просмотр. Java отвечает `206`; базовый клиент проверяет совпадение `Content-Range` с запросом и реального размера с заголовками. Если сервер проигнорировал Range, такой ответ отклоняется.

Для предпросмотра передаётся меньше данных. Это запрос диапазона байтов, а не автоматическое возобновление скачивания или протокол границ текста. Префикс может закончиться посередине UTF-8 символа; пример корректно завершает работу декодера.

## 5. Подключить свой интерфейс и смену аккаунта

Используйте `useFileUpload` или `useFileDownload` со своими компонентами; `TransferStatus` необязателен. Hooks возвращают `state`, `cancel()` и `reset()`. Загрузка дополнительно предоставляет `uploadFile(key, blob)` и `upload({key,source,knownLength?,contentType?})`; скачивание — `download(key,destination,range?)`. Методы возвращают promises: обрабатывайте rejection, даже если показываете `state`.

| Состояние | Значение |
| --- | --- |
| `idle` | В этой области ещё нет операции |
| `transferring` | Данные передаются либо ожидается подтверждение upload / закрытие назначения |
| `complete` | Получено проверенное подтверждение upload или завершено назначение download |
| `failed` | В `error` исходная причина; `TransferError.uploadOutcome` различает `not-started`, `rejected`, `unknown` для upload |

Вход пакета сохраняет директиву `'use client'` для клиентской границы фреймворка; при импорте browser globals не используются. Меняйте `scope` при смене аккаунта, tenant или области авторизации. Смена scope/endpoint отменяет старую операцию и скрывает её состояние; unmount тоже отменяет. Компонент сбрасывает выбранный файл при смене ключа/scope. Старый promise может завершиться позднее, но не обновит UI новой области. Отмена кооперативна и не доказывает откат на сервере; пользовательский sink должен правильно поддерживать отмену.

Один hook допускает одну активную передачу. Для независимых файлов создавайте отдельные экземпляры; общий бюджет параллельности выбирает приложение. Не используйте повторно источник или назначение предыдущей попытки. `reset()` сбрасывает отображение после завершения, но не удаляет объект.

`labels` задаёт текст кнопок и статусов; доступны `russianLabels` и `englishLabels`. Через `className`, семантические элементы, обычные кнопки и `renderError` компоненты встраиваются в существующий дизайн. CSS в пакет не включён. Заголовки доступа передавайте через `headers`, а `credentials` задавайте в соответствии с CORS-политикой приложения.

## 6. Запустить парный пример

Нужны соседние checkout-каталоги `file-streams`, `file-streams-spring-boot-starter`, `file-streams-react`, Node 22.12+, npm, JDK 17+ и OpenSSL. Используются локально собранные артефакты; публикация в npm/Maven не предполагается.

```bash
# Из file-streams-react подготовьте базовые артефакты.
(cd ../file-streams && ./gradlew publishToMavenLocal -PtestJavaVersion=17 \
  -Dmaven.repo.local="$PWD/build/local-repository")
(cd ../file-streams/browser && npm ci && npm run build)
npm ci
npm test
npm run typecheck
npm run test:package
```

Терминал 1 — ограниченный **тестовый fixture в памяти**, без S3 credentials:

```bash
cd ../file-streams-spring-boot-starter
scripts/run-example.sh :example:runTransportFixture
```

Терминал 2 — из этого репозитория:

```bash
npm run demo
```

Откройте `https://127.0.0.1:5173/` и доверьте локальному сертификату разработки оба порта: 5173 и 19443. Выберите небольшой файл, загрузите, дождитесь записи с подтверждением и скачайте. Демо использует сертификат, созданный стартером; пути можно переопределить через `DEMO_TLS_CERT` и `DEMO_TLS_KEY`.

Для настоящего S3-совместимого хранилища следуйте [инструкции стартера](https://github.com/59Alex/file-streams-spring-boot-starter#readme), передайте credentials стандартной цепочкой AWS и запустите `scripts/run-example.sh` без аргумента fixture. Fixture находится только в тестовых исходниках примера и не является production-адаптером.

При запущенных серверах `npm run test:browser` проверяет настоящее взаимодействие Chromium → Spring по HTTP/2 и равенство байтов PUT/GET. Диалог сохранения в этой проверке заменён тестовым writable sink; это не автоматизация системного диалога.

## 7. Подключить форму React 19

Отдельный entry `@59alex/file-streams-react/react19` полезен для формы, уже использующей Actions. [ActionAttachment.tsx](../../examples/attachments/ActionAttachment.tsx) соединяет именованное файловое поле с тем же Java PUT endpoint. Hook даёт pending, потоковый прогресс, отмену и проверенный результат без дополнительного submit-обработчика. Основной entry остаётся совместимым с React 18.

См. [полный контракт Action](reference.ru.md#actions-формы-react-19): очередь, очистка файлового поля после попытки, синхронная смена scope и неизвестный результат. Это клиентский Action, не Server Function; оптимистичного «сохранено» нет.

## Диагностика и границы проверки

- `A transfer is already active`: дождитесь завершения promise; для другого файла нужен отдельный hook.
- `This transfer belongs to an old scope`: не сохраняйте callbacks через смену аккаунта; используйте результат текущего render.
- `UNSUPPORTED` или ошибка потокового запроса: проверьте браузер, доверенный TLS, HTTP/2 и работу прокси; не заменяйте передачу накоплением целого файла.
- При скачивании недоступны метаданные: откройте необходимые заголовки через CORS.
- `uploadOutcome: unknown`: сначала проверьте состояние в приложении/хранилище, затем решайте, нужен ли новый поток и повтор.
- Ошибка сертификата или готовности: сначала запустите Spring-пример и проверьте разрешённые origins.

Локально проверены восемь содержательных lifecycle/transfer/Action тестов, строгая компиляция примеров, установка npm-архива в чистый consumer с SSR, Chromium HTTP/2 upload/commit/download и отмена с известной длиной через Spring Boot 4.1.2. [Подробная проверка](../VERIFICATION.md). Парный запуск использовал ограниченный fixture в памяти, **не S3**. полный браузерный сценарий React 18, upload в Safari/Firefox, системные диалоги сохранения, обрывы сети и production-прокси не проверялись. Отдельные результаты хранения и границы надёжности описаны в [базовой библиотеке](https://github.com/59Alex/file-streams).
